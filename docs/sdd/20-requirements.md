# 20. 요구 정의 (3차 사이클 — 프리셋 테마·재적용)

- 원 요청(2026-11-09): «그러면 토큰에 대해서 다시 잘 적용할 수 있도록 하고, 미리 준비된 디자인도 사용할 수 있게 할꺼지?» — 2차 사이클(단일 출처·감사·한 줄 설치) 위에 ①**재적용**(받은 토큰의 갱신·교체) ②**프리셋**(미리 준비된 디자인 세트)을 얹는다.
- 전제: 2차 산출(AC-9~12)은 회귀 없이 유지. 본 문서의 AC는 AC-13~16(전 사이클 AC-1~12 연속 번호).

## 1. 기회·위험

| # | 내용 | 대응 |
|---|---|---|
| R-1 | `shadcn add theme.json` **재실행 동작** — 프리셋 교체(다른 프리셋 add)가 전적으로 이 동작에 의존. **G0 병행 조사(2026-11-09)로 실측 완료**: 복제 소비자에서 같은 theme 재add → 멱등(파일 무변화·변수 수 불변), 값이 다른 theme으로 재add → 기존 변수 **그 자리 값 치환**(이전값 잔존 0·블록 증식 없음) → fallback 불필요. 공식 실증은 AC-14가 담당 | 제약 2건(F-29 반영): ① **일괄 add(`/r/registry.json` 전체 설치) 경로는 범위 밖** — 프리셋 add는 항상 개별 theme URL로만 안내·실증(AC-16 README 연동) ② AC-14 실증은 `-y`만 사용(플래그 없음, 2차 실측 조건 고정 — `--overwrite` 등 유무가 변수가 되지 않게 차단) |
| R-2 | 프리셋 색 값의 품질 — 아무 색이나 넣으면 대비 부족으로 접근성 훼손(1차가 destructive 조정으로 WCAG AA를 챙긴 전례) | 기계 계산 가능한 최소 기준: 프리셋별 핵심 전경/배경 쌍의 대비비 ≥ 4.5:1(라이트 기준)을 증명 단계에서 계산. **값 출처는 Tailwind 공식 패키지 팔레트에서 계산**(기본 zinc 현행값이 팔레트 유도값과 정확히 일치함을 G0 조사로 실측 — shadcn 테마와 동일 재료) — 본문 전체에서 이 출처 표기로 통일(F-33) |
| R-3 | 프리셋 수·이름 정책 부재 — 많이 만들면 유지 비용, 적으면 의미 없음 | 기본(zinc) + **3종**. 이름·색상은 설계(G1)에서 확정하고 요구는 «기본 포함 4 theme 항목»으로 고정 |
| R-4 | 감사(8검사)·카탈로그가 프리셋을 모르면 사각 발생 — 2차 감사는 theme 항목 1개·토큰 20종 가정 | AC-15로 감사 확장(생성 역방향 다중 항목), AC-16으로 카탈로그·README 갱신 |

## 2. 용어

- **프리셋**: 이름 붙은 토큰 20종 전체 세트(라이트+다크). 기본(zinc)도 프리셋의 하나로 취급.
- **재적용**: 이미 토큰을 받은 소비자 프로젝트에 다시 `add`하는 것 — (a) 같은 프리셋 재실행(값 갱신) (b) 다른 프리셋으로 교체.

## 3. 완료 기준 (AC-13~16 — 전부 기계 관찰 가능)

### AC-13 프리셋 단일 출처·생성
프리셋 정의는 `packages/unikit/src/theme/` 안 **소스 파일 하나**에만 존재하고(값 사본 금지 원칙 준수), `bun run generate:design`이 registry에 **theme 항목 4개**(기본 + 프리셋 3)를 생성한다. 증명: (a) 생성 멱등(재실행 산출 불변) (b) registry의 각 theme 항목이 생성물과 일치 — 검증 수단은 생성물 재출력과의 독립 대조, 또는 AC-15 (a) 감사(둘 중 하나로 증명; 감사 사용 시 AC-15가 선행·동시 검증됨을 인정 — F-30) (c) 프리셋별 값 형식 전수(키 20종·HSL 채널 문자열·radius 1종) (d) 프리셋별 핵심 쌍(background↔foreground, primary↔primary-foreground) 라이트 대비비 ≥ 4.5:1 계산 증명.

### AC-14 소비자 설치·재적용 실증
신규 소비자(2차 T-15와 동일 절차·동일 조합 생성 — §5)에서 전부 1줄 명령(`-y`만, 플래그 고정)으로: (1) 프리셋 P 설치 → `:root`/`.dark` 각 20값이 P의 값과 전부 일치(hsl() 래핑 허용) (2) **다른 프리셋 Q로 재적용** → 20값이 Q로 교체(P 잔존 0, 변수 중복·블록 증식 없음) (3) 같은 프리셋 재실행 → 멱등(값 불변). 관찰 수단은 **중괄호 깊이 블록 파서**(이번 사이클 산출물로 제작 — G1 태스크에 등재, F-31)와 grep. (조사 단계에서 (2)(3) 동작을 사전 실측해 뒀다 — R-1 — 공식 실증은 본 AC 절차로 재현한다.)

### AC-15 감사 확장
`bun run audit:design`가 다중 theme 항목을 커버: (a) registry의 모든 theme 항목(식별은 **`type: "registry:theme"` 필드 기반** — 이름 우연 매칭 방지, 감사자 권고) == 각 프리셋 생성물(기존 (a2)의 다중화) (b) **프리셋 값을 정의하는 소스 파일 전부**를 원색 검사 (b)의 제외 목록에 반영(tokens.ts와 동일 취급 — 프리셋 파일들은 값의 출처. 정의 파일 수는 설계에 무관하게 이 기준이 성립하도록 일반화 — F-32) (c) 기존 검사 (a1)(b)(c)(d)(e)(f)(g) 회귀 없음(현 트리 PASS 유지). 음성 시험: 프리셋 1값 오염(소스·registry 각 1건) → exit 1.

### AC-16 문서 갱신
생성 카탈로그 `docs/tokens.md`에 프리셋 목록과 기본 프리셋 값 표(생성물), README에 ①프리셋 선택 안내(항목별 add 한 줄) ②재적용·교체 절차가 실증 동작과 일치하는 안내. 완료 기준: README·docs/components.md에서 HSL 리터럴 0건 유지(값은 카탈로그와 프리셋 소스에만).

## 4. 범위 밖 (명시적 비목표)

- **provider 런타임 프리셋 전환**(모노레포 앱에서 JS로 프리셋 바꾸기) — 2차 §4에서 provider API 확장을 범위 밖으로 둔 판단 유지. 소비자(복사본) 경로의 CSS 변수 교체가 이번 범위.
- **모양(스타일) 프리셋** — radius·간격·크기 조합은 값 1종 유지. 색 프리셋만.
- **사용자 임의 프리셋 작성 도구**(CLI로 커스텀 테마 굽기) — 문서 안내(«CSS 변수값을 직접 고친다»)로 충분.
- **쇼케이스 UI 변경** — 데모 앱은 기본 zinc 그대로(1차 G4/G5 증거 보존).
- **F-11 실물 확인** — 계속 별도 추적(03 문서 §7.3).

## 5. 제약

- bun 1.4.4 전용(pnpm 금지 — 기존 정책). 커밋 0 유지(사용자 요청 시에만).
- 2차 감사 8검사는 현 트리에서 계속 PASS(회귀 금지). 감사 검사 표기 «요구 7종/내부 8건»은 다중 항목 반영 후에도 문서·출력이 일치하도록 갱신.
- 소비자 실증은 /tmp 신규 생성 — **2차 실측 조합을 그대로 재현한다(F-28)**: create-next-app 최신 → `shadcn init` → `tailwindcss@3.4` 강등하되 **init이 생성한 globals.css는 TW4 문법(`@theme inline` 등)이 잔존하는 혼재 상태**. hsl() 래핑 관찰은 이 조합 기준이다. 기존 /tmp/my-unikit-app은 2차 증거로 보존(미변경).
- shadcn CLI 4.23 실측 기준(상위 버전 호환은 보장하지 않는다는 한계를 문서에 유지).

## 6. 환경 사실 (실측 근거)

- `registry:theme` 스키마 통과·`add .../r/theme.json` 1회 주입(:root/.dark 20/20, TW4 소비자에서 `hsl()` 래핑 — 값 무손실) — 2차 13 문서 §3. 레지스트리 서빙은 `force-dynamic` 런타임 로드(빌드 불필요).
- shadcn 4.23 dist에 `transformCssVars`/`updateCssVars` 존재(값 갱신 경로가 코드상 있음 — 재적용 동작의 작동 가능성 근거. 실행 검증은 R-1).
- 소비자 globals.css는 TW4 문법(`@theme inline`) — **단 소비자 패키지는 TW 3.4(강등)와 혼재(2차 실측 조합)**. 프리셋 값 주입 형식도 hsl 래핑 예상(조사 단계 재실험에서 동일 래핑 관찰).
- **재적용 동작 실측(2026-11-09 조사)**: 같은 theme 재add → 멱등. 값 변조 theme 재add → 그 자리 값 치환(잔존 0·블록 불변). 실험은 복제 소비자(/tmp/reapply-probe)에서 수행, 저장소 레지스트리는 byte 원복 + 감사 exit 0 확인 완료.
- 2차 감사의 (a2)는 theme 항목 1개 가정 하드코딩(`find name==="theme"` — audit-design.ts:83) — 다중화 필요(AC-15).

## 7. 막힌 질문·설계 확정 예정

막힌 질문은 없음. 설계(G1)에서 확정할 사항: 프리셋 색상·이름(R-3, 값 출처는 R-2의 «Tailwind 공식 팔레트 계산 + 대비 검증»으로 통일 — F-33 반영), **기본 theme 항목의 이름을 «theme»으로 유지(README 기존 안내 호환)할지 «theme-zinc»로 개명할지**, theme 항목 감사 필터의 type 기반 전환 상세(AC-15 (a) — 권고 채택됨).
